CM ROUTE — ЛОГИКА РАБОТЫ ПО БЛОКАМ И КАК МЫ ТЕСТИРОВАЛИ
========================================================

Прототип для кейса СМ-Клиники «Не потерять пациента».

Что делает система:
- находит в протоколе УЗИ клинически значимые находки;
- показывает их администратору (он же врач) с объяснением, почему сработало;
- после подтверждения ведёт пациента до консультации профильного специалиста нейтральными уведомлениями.

Принципы:
- распознавание только локальное, внешние LLM и облака не используются;
- данные обезличены;
- система не ставит диагноз;
- пациенту не сообщаем, что именно найдено.

Содержание
  1. Логика работы по блокам
  2. Как тестировали
  3. Что решает медэксперт
  4. Подробные пояснения к коду и история правок


1. ЛОГИКА РАБОТЫ ПО БЛОКАМ
==========================

Путь одного протокола:

  МИС / файл / интерфейс
    → [1] приём
    → [2] обезличивание
    → [3] разбор текста
    → [4] находки по правилам
    → [5] второй контур
    → [6] маршруты
    → [7] уведомления и напоминания
    → [8] кабинет пациента
    → [9] администратор видит всё в интерфейсе

Всё, что может меняться (словарь, маршруты, тексты, сроки), лежит в config/*.yaml или в базе (правки администратора).
Код эти настройки только читает.


Блок 1. Приём протокола — app/main.py
-------------------------------------
Источники:
- вебхук МИС POST /api/events: protocol.signed / corrected / cancelled и события записи;
- ручная загрузка файла POST /api/upload;
- папка data/inbox, которую сервис проверяет раз в 3 секунды.

Форматы файлов:
- PDF читает pdfplumber;
- .docx читает python-docx: абзацы и ячейки таблиц по порядку, дубли объединённых ячеек убираются;
- .txt читается как есть.

Защита от дублей:
- повторный event_id не создаёт второй маршрут;
- event_id файла — это хэш содержимого.

Ошибка в данных возвращает 400 и откатывает обработку целиком, поэтому событие можно прислать снова.

Доступ:
- все эндпоинты закрыты токеном;
- у МИС и администратора разные токены;
- демо-функции (модельное время, демо-данные) работают только при CM_ENV=demo.


Блок 2. Обезличивание — app/nlp/anonymize.py
--------------------------------------------
- ID пациента из МИС превращается в псевдо-ID: HMAC-SHA256 с секретной солью CM_PSEUDO_SALT.
  Без соли псевдо-ID нельзя обратить перебором.
- Из текста удаляются:
  - строки-шапки «ФИО:», «Пациент:», «Дата рождения:»;
  - «Фамилия И.О.»;
  - телефоны.
- В базу, журнал и интерфейс попадает только обезличенный текст. В лог сервера тексты не пишутся, только ID.


Блок 3. Разбор текста — app/nlp/normalize.py
--------------------------------------------
- Текст делится на предложения (. ! ? ; перевод строки) и части предложения (запятая, двоеточие, скобка, тире).
  Десятичная запятая «1,2 см» границей не считается.
- Слова приводятся к начальной форме офлайн-анализатором pymorphy3. Без него сервис не стартует.
  Запасной стеммер Snowball (код из NLTK, лицензия Apache 2.0) включается только явно: CM_ALLOW_NO_MORPH=1.
- Опечатки ловит нечёткое сравнение (rapidfuzz, порог 85), включая перестановку соседних букв.
  Оно работает только для незнакомых слов: обычное русское слово «простой» не станет «простатой».
- Аббревиатуры (ОБА, ЖП, ЧЛС) в словаре пишутся ЗАГЛАВНЫМИ и совпадают только буква в букву.


Блок 4. Находки по правилам — app/nlp/extractor.py + config/findings.yaml
-------------------------------------------------------------------------
Словарь:
- 37 групп органов с синонимами;
- 38 находок, у каждой задан маршрут к специалисту (одна выключена до решения медэксперта).

Как находка попадает в кандидаты (два способа):
  а) самостоятельный термин: «холецистолитиаз», «аденомиоз», «варикоцеле»;
  б) правило «ЧТО + ГДЕ»: «образование» + ближайший орган «яичник» = образование яичника.
     - Орган ищется в той же части предложения, затем в предложении.
     - Если в предложении органа нет, берётся заголовок раздела: строка «Желчный пузырь:» задаёт орган для следующих предложений.
     - Справочные органы (лимфоузлы, маточная труба) открывают раздел, только если строка — заголовок.

Фильтры от ложных срабатываний (в таком порядке):
  1. Рекомендация врача УЗИ. Текст после «рекомендовано» — это рекомендация, а не находка.
     Админ получает сигнал, если находка есть только там.
  2. Исключения словаря и администратора.
     - «Тромб» рядом с «аортой» — это не тромбоз вен ног.
     - Исключение действует в своей части предложения или во всём предложении (exclude_scope: sentence).
  3. Отрицание:
     - перед находкой («без», «не выявлено», окно 6 слов);
     - после находки (окно 8 слов);
     - через перечисление: «Без полипа, гиперплазии»;
     - «не» прямо перед словом: «аорта не расширена»;
     - форма «ключ: значение»: «Объёмные образования: не выявлены».
  4. Неуверенность («не исключён», «?», «дифференцировать с»). Находка остаётся, но с пометкой «проверить».
  5. Анамнез («удалён», «состояние после»). Слова «вновь», «рецидив» анамнез отменяют.
  6. Числовые условия:
     - размер полипа ЖП ≥ 10 мм;
     - BI-RADS ≥ 3;
     - стеноз артерий ног ≥ 40 %, сонных ≥ 50 %;
     - аорта ≥ 30 мм.
     Если в тексте нет числа — пометка «проверить» (или «не считать», если так задано в словаре).
     Размер может браться из другого места протокола, с пометкой.
     Категория BI-RADS из всего текста применяется, только если она в протоколе одна.
  7. Поглощение. «Патология эндометрия (полип)» — показывается только более точная находка, «полип эндометрия».

Результат:
- по каждой находке: цитата, правило, версия словаря, атрибуты, уверенность и пометки;
- отклонённые кандидаты с причиной — блок «Не сработало и почему».

Администратор дополняет словарь без программиста:
- «Словарь» → «Ручное добавление»: термин, «что», синоним органа или новая находка;
- «Словарь» → «Исключения».
Всё хранится в базе и действует сразу.


Блок 5. Второй контур — app/nlp/ml_layer.py, ml_features.py
-----------------------------------------------------------
Это не нейросеть, а две небольшие обучаемые модели: TF-IDF по буквосочетаниям и словам + логистическая регрессия (scikit-learn).
Обучение занимает секунды на CPU, GPU не нужен.

- Детектор пропусков:
  - для каждого предложения оценивает, похоже ли оно на находку, которую правила не нашли;
  - выше порога 0.9 добавляет находку с пометкой «найдено вторым контуром — проверить».
- Верификатор:
  - оценивает каждую находку правил;
  - ниже порога 0.4 ставит пометку «вероятно ложное»;
  - находку не удаляет, а только помечает;
  - судит только типы, где в обучении было ≥ 5 настоящих примеров;
  - не спорит с правилом, если правило само измерило размер или BI-RADS и порог выполнен.
- Находки второго контура никогда не уходят пациенту автоматически.
- Модель: models/second_layer.joblib. Обучение: scripts/train.py.
  Перед сохранением скрипт проверяет, что в словаре модели нет ФИО из шапок протоколов.


Блок 6. Маршруты — app/routing.py + config/routes.yaml
------------------------------------------------------
Создание маршрутов:
- находки с одним маршрутом (например, полип и гиперплазия эндометрия) дают один маршрут к одному специалисту;
- разные маршруты дают разные карточки;
- у каждого маршрута есть приоритет (1–3) и целевой срок (target_days).

Экстренные находки (острый холецистит, тромбоз глубоких вен, внематочная беременность):
- сразу уходят персоналу;
- пациенту автоматически не пишем;
- если маршрут не принят за 15 минут — повторная эскалация.

Плановые находки ждут проверки администратора. Без проверки пациенту можно отправлять (вкладка «Настройки»):
- в режимах «все плановые», «врач УЗИ сам рекомендовал этого специалиста», «выбранные специалисты»;
- в режиме «по своим правилам»: пользовательские сценарии.

Правило из пользовательского сценария срабатывает, когда выполнены все его условия:
- специалист;
- только эти находки;
- приоритет;
- уверенность не ниже заданной;
- врач УЗИ рекомендовал этого специалиста;
- тип исследования содержит заданный текст.

Даже если правило подошло, пациенту не отправляется:
- экстренное;
- находка второго контура;
- находка с пометкой «проверить» (по умолчанию).

Кнопка «Проверить на текущих маршрутах» показывает, сколько маршрутов ушло бы сразу, ничего не меняя.

Исправленный или аннулированный протокол:
- находки пересчитываются;
- маршруты обновляются, закрываются или открываются снова;
- если пациенту уже писали, админ получает задачу.

Машина состояний (ALLOWED) запрещает бессмысленные действия, например «приём состоялся» на неподтверждённом маршруте.
Все действия пишутся в журнал: кто, что, когда, на каком основании.


Блок 7. Уведомления и напоминания — app/notify.py, routing.tick()
-----------------------------------------------------------------
- Тексты пациенту нейтральные: «плановая консультация врача-…», «незавершённый маршрут обследования».
  Находка не называется.
- Лестница напоминаний задана в routes.yaml:
  - 24 ч — сообщение;
  - 72 ч — SMS и пуш;
  - 7 дней — задача админу позвонить (скрипт без названия находки);
  - 14 дней — мягкое напоминание;
  - 30 дней — «не вовлечён».
- Администратор меняет тексты и лестницу в «Настройках» → «Сценарий уведомлений». Можно добавлять свои шаги и тексты.
- Встроенная проверка нейтральности не даёт сохранить текст пациенту:
  - если в нём пугающие или медицинские слова (рак, онко, киста, узел, тромб, срочно, изменения, отклонение, диагноз…);
  - если словарь находит в тексте находку.
- Антиспам:
  - не больше 2 отправок пациенту в сутки, лишние переносятся на 10:00 следующего дня;
  - после записи, приёма или отказа отложенные сообщения отменяются.
- Планировщик:
  - в бою — фоновый поток раз в минуту;
  - в демо — кнопки модельного времени.
- После простоя выполняется только последний созревший шаг, но звонок админу не пропускается.


Блок 8. Кабинет пациента и телефон — app/main.py (/api/patient/...), static/index.html
---------------------------------------------------------------------------------------
- При запуске интерфейс спрашивает роль: «Администратор» или «Пациент».
- Кабинет пациента — эмулятор ЛК МИС. В нём:
  - нейтральный баннер;
  - лента сообщений;
  - шаги «Плановая консультация врача-…» с ближайшими слотами;
  - кнопки «записаться», «уже был(а) у врача», «не планирую».
- В кабинет не попадают:
  - названия находок;
  - текст протокола;
  - неподтверждённые и экстренные маршруты.
- Телефон-заглушка:
  - экран блокировки с пуш-уведомлениями и SMS;
  - routes.yaml → push_on_lock_screen: generic скрывает текст пуша на экране блокировки.
- «Включить уведомления браузера» показывает новые пуши системным уведомлением компьютера через Notification API браузера.
  Внешние пуш-сервисы не используются.
- Настоящий пуш делается через приложение или ЛК клиники.
  Контракт тот же: notify.to_patient(псевдо-ID, текст, каналы).

Одна страница без сборки и внешних библиотек. Вкладки:
- Очередь: экстренные сверху, затем ждущие проверки.
- Карточка маршрута:

  - «Не сработало и почему»;
  - действия;
  - сообщения пациенту;

- Дашборд: воронка «находка → уведомление → запись → приём» и экономика.

- Словарь: ручное добавление и исключения.
- Настройки: автоотправка, правила и сценарий уведомлений.


Блок 10. Хранение и безопасность — app/store.py, app/config.py
--------------------------------------------------------------
- Локальная база SQLite в режиме WAL. Обработка события — одна транзакция, при ошибке откатывается целиком.
- event_id занимается атомарно (INSERT OR IGNORE).
- Конфиги YAML перечитываются при изменении. Битый конфиг не применяется: остаётся последняя рабочая версия.
- Docker:
  - непривилегированный пользователь;
  - код и конфиги только для чтения;
  - наружу — только через reverse proxy с TLS.


2. КАК ТЕСТИРОВАЛИ
==================

2.1. Данные
-----------
- data/real — 89 протоколов, выданных организаторами. 6 типов исследований:
  - органы малого таза;
  - брюшная полость и ЖП;
  - молочные железы;
  - щитовидная железа;
  - простата;
  - сосуды ног.
  Из них 53 с находками и 36 норм, всего 68 находок.
  Размечал разработчик по стандартной терминологии, а не врач. Лежат в репозитории — держите его приватным.
- data/web — 57 протоколов из открытых источников. Это более честная проверка, потому что словарь писали, глядя на data/real.
- data/synthetic — синтетика только для кнопки «Демо-данные». В метриках не участвует: команда признала её невалидной.

2.2. Метрики
------------
- TP — находка есть и в разметке, и у системы.
- FP — система нашла, в разметке нет: лишняя находка, лишняя работа админа.
- FN — в разметке есть, система не нашла: пропуск, самое опасное.
- Пропуски (FN-rate) = FN / (TP + FN). Ложные (FDR) = FP / (TP + FP).
- Нормы с ложным срабатыванием: в скольких нормальных протоколах система что-то нашла.
- Уровень маршрутов (протокол × специалист): именно он решает, дойдёт ли пациент.

Команды (из корня проекта, Windows: перед ними $env:CM_ENV="demo"):
  CM_ENV=demo python scripts/evaluate.py data/real/protocols.jsonl           # правила + второй контур
  CM_ENV=demo python scripts/evaluate.py data/real/protocols.jsonl --no-ml   # только правила
  CM_ENV=demo python scripts/evaluate_ml.py data/real/protocols.jsonl --repeats 3 --folds 5 --extra-train data/web/protocols.jsonl
  CM_ENV=demo python scripts/evaluate_transfer.py --miss 0.9 --fp 0.4
  CM_ENV=demo pytest -q tests

2.3. Результаты правил (словарь 0.6)
------------------------------------
                         находок   пропуски        ложные           нормы с ложным
  реальные (89)          68        0 (0 %)         6 из 74 (8,1 %)  4 из 36
  интернет (57)          34        2 (5,9 %)       6 из 38 (15,8 %) 3 из 26

Для сравнения: в версии v4 на реальных было 13 ложных (16 %) и 10 норм с ложным срабатыванием,
на интернет-наборе — 3 пропуска и 10 ложных.

Все оставшиеся ошибки — вопросы клинической политики (раздел 3), а не баги кода.
Шестая «ложная» на реальных — гемангиома печени. Это настоящая находка, но в разметке её нет:
разметка делалась только по шести типам исследований из кейса.

2.4. Второй контур
------------------
Как проверяли честно, чтобы модель не проверялась на тех же протоколах, на которых училась:
- Кросс-валидация по протоколам: 5 частей × 3 повтора, StratifiedGroupKFold.
  - Дубли протокола всегда попадают в одну часть.
  - Интернет-набор добавлялся только в обучение, в тест не попадал.
- Перенос: обучили на одном наборе, проверили на другом (реальные ↔ интернет) при рабочих порогах 0.9 / 0.4.

Что получилось:
- Детектор пропусков:
  - различает предложения с находкой хорошо: ROC AUC 0,965 вне обучения;
  - на реальных правила ничего не пропускают, поэтому спасать нечего, а лишних подсказок он добавляет
    (порог 0,5: 25 на 89 протоколов);
  - при переносе реальные → интернет два пропуска правил (острый холецистит без слова «острый») НЕ поймал.
    На своих данных (в обучении) поймал оба. Пользу детектора на новых данных пока доказать не удалось.
- Верификатор:
  - помечает треть ложных срабатываний правил и почти не задевает настоящие (0,5 %); ROC AUC 0,757;
  - при переносе реальные → интернет в режиме «убирать» снижает ложные с 6 до 4 без новых пропусков;
  - при переносе интернет → реальные режим «убирать» дал 10 пропусков (14,7 %).
  Поэтому в системе он только ПОМЕЧАЕТ «вероятно ложное» и ничего не удаляет.
- В рабочей конфигурации (правила + контур, оценка на тех же данных, поэтому оптимистично):
  - реальные: 0 пропусков, 9 ложных;
  - интернет: 0 пропусков, 10 ложных.

Вывод: основная работа — на правилах. Контур — подсказка администратору, которой нужно больше данных.
Переобучать стоит на выгрузке МИС с разметкой врача.

2.5. Расширение словаря 0.6 (популярные органы)
-----------------------------------------------
Добавлены 16 находок:

3. ЧТО РЕШАЕТ МЕДЭКСПЕРТ
========================
- Полип ЖП без размера: показывать с пометкой «проверить» (сейчас) или не считать.
- «Дифференцировать с X» — считать ли альтернативную гипотезу поводом для маршрута.
- Функциональная киста и «эндометриома?»: что важнее, описание или заключение.
- «Начальные проявления атеросклероза» без процента стеноза.
- Гистология в блоке рекомендаций — текущая находка или нет.
- Признаки острого холецистита без слова «острый»: список признаков даёт хирург.
- Пороги:
  - полип ЖП ≥ 10 мм;
  - BI-RADS ≥ 3;
  - стеноз ног ≥ 40 %, сонных ≥ 50 %;
  - аорта ≥ 30 мм.
- Новые находки словаря 0.6:
  - нужна ли гепатомегалия;
  - куда направлять лимфоузлы и слюнные железы;
  - что считать значимым в почке (кисты Bosniak).
- Тексты пациенту и список запрещённых слов — вместе с юристом.

app/nlp/extractor.py
--------------------

[модуль]
ИЗВЛЕЧЕНИЕ НАХОДОК из текста протокола. Полностью локально, без внешних LLM.

Как это работает (по шагам, для каждого протокола):
  1. Текст режем на слова и приводим слова к начальной форме (normalize.py).
  2. Предложения с рекомендациями врача УЗИ («рекомендована консультация гинеколога»)
     не считаем описанием находки, но запоминаем, какого специалиста рекомендовали.
  3. Для каждой находки из словаря ищем:
       а) самодостаточные термины («холецистолитиаз»);
       б) пары «ЧТО + ГДЕ» («полип» + ближайший орган = «эндометрий»).
  4. Каждого кандидата проверяем: отрицание («не выявлено»), анамнез («удалён»),
     исключения («фолликулярная»), числовые условия (размер, BI-RADS), неуверенность.
  5. Возвращаем: принятые находки (с цитатой, правилом, атрибутами, уверенностью)
     и отклонённые кандидаты (с причиной — это объяснение «почему не сработало»).

Решение о маршруте здесь НЕ принимается — это делает routing.py по матрице.

1) есть общая начальная форма -> точное совпадение; 2) иначе ищем опечатку.

[_match]

Но «Эндометрий без особенностей, полип 7 мм» — НЕ список находок, отрицание не наследуется.

app/nlp/ml_features.py
----------------------

[модуль]
Признаки для ВТОРОГО КОНТУРА. Общие для обучения (scripts/train.py) и работы (ml_layer.py),
чтобы модель в бою видела ровно то же, на чём училась.

Два вида объектов:

  2) КАНДИДАТ правил (принятый или отклонённый) — вход верификатора (FP): «правда ли это находка».

[sentence_input]

app/nlp/ml_layer.py
-------------------

[модуль]
ВТОРОЙ КОНТУР — обучаемые модели поверх правил. Первый слой (extractor.py) — это фильтр
на словаре и правилах, «ИИ» там нет. Здесь — две модели, обученные на размеченных протоколах:

  1) ДЕТЕКТОР ПРОПУСКОВ (борется с ложноотрицательными, FN)
     а) по каждому ПРЕДЛОЖЕНИЮ: «описана ли тут значимая находка и какого типа» (TF-IDF + логрегрессия).
        Ловит то, чего нет в словаре (миома, ДГПЖ, варикоз…) и непривычные формулировки;
     б) по ОТКЛОНЁННЫМ кандидатам правил: «правило отклонило зря?» (тот же верификатор, см. ниже).
     Результат — находка с пометкой «найдено вторым контуром — проверить». Сам маршрут
     без админа не запускается.

  2) ВЕРИФИКАТОР (борется с ложноположительными, FP)
     По каждому ПРИНЯТОМУ кандидату правил: вероятность, что находка настоящая. Учитывает текст,
     правило, пометки и то, что правила решили по этому же типу в других местах протокола
     (например, «полип 3,5 мм — условие не выполнено» в описании и «Полип ЖП» без размера в заключении).
     Низкая вероятность -> пометка «второй контур: вероятно ложное». Находка НЕ удаляется:
     решение остаётся за админом, а очередь сортируется с учётом этой оценки.

Модели никогда не отменяют решение правил молча и не принимают решение о маршруте.

[MissDetector]
FN: предложение -> P(в нём описана находка типа T) для каждого типа (один-против-всех).
Общие признаки TF-IDF, отдельная логрегрессия на каждый тип; тип с <2 примерами не учим.

[SecondLayer.fit]
protocols: [{"text", "expected": [{"id", "quotes": [...]}]}]; extract_fn(text) -> ExtractionResult без модели.

[SecondLayer.decide]
Что скажет второй контур. Ничего не меняет; возвращает:
verifier: {тип: P(настоящая)} для находок, ПРИНЯТЫХ правилами;
rescued:  {тип: (P, кандидат)} — правила отклонили, модель считает находкой;
missed:   {тип: (P, предложение)} — правил не было вовсе, детектор нашёл.

[SecondLayer.apply]
Встроить решения в результат извлечения: пометки, новые находки «на проверку», сортировка.

[training_rows]
Разметка протокола -> обучающие строки обоих модулей.
Предложение положительно для типа T, если содержит одну из цитат T из разметки.
Кандидат правил «настоящий», если тип T есть в разметке протокола.

app/nlp/normalize.py
--------------------

[модуль]
Нормализация текста: токены, леммы (начальные формы слов), предложения, части предложений.

Почему так: врачи пишут одно и то же по-разному («полипа эндометрия», «полипы эндометрия»,
«полипп эндометрия»). Приводим каждое слово к начальной форме (лемме) — тогда словарь
можно писать в одной форме, а совпадение найдётся в любой.
Всё работает ЛОКАЛЬНО: pymorphy3 — офлайн-словарь русского языка, никуда не ходит по сети.

[norm_text]
Нижний регистр и ё->е. Длина строки НЕ меняется — позиции символов совпадают с оригиналом.

[lemma_variants]
ВСЕ возможные начальные формы слова. Нужно для омонимов: «железы» -> {железа, железо}.
Слово текста и слово словаря совпадают, если у них есть общая начальная форма.

[is_known_word]
Это обычное слово русского языка из словаря pymorphy3 («простой», «точка», «узел»)?
НОВОЕ v5: такие слова НЕ подменяются нечётким сравнением на органы и термины.
Опечатка почти всегда даёт НЕсуществующее слово («полипп», «эндомерия», «пзуыря») — их и ищем нечётко.
Было: «простой кисты яичника» -> «простой» ≈ «простата» -> орган = простата -> киста яичника терялась молча.

[_stem]
Запасной стемминг без словаря (только при CM_ALLOW_NO_MORPH=1): Snowball, а если его нет — отрезаем окончание.

[similar]
Похожесть двух слов 0..1 с учётом опечаток. Короткие слова (<5 букв) — только точное совпадение.

scripts/evaluate.py
-------------------

[модуль]
ОЦЕНКА КАЧЕСТВА: сколько находок найдено правильно, сколько лишних, сколько пропущено.

Запуск:  python scripts/evaluate.py [путь_к_разметке.jsonl] [--split dev|holdout|all]

Формат разметки (одна строка = один протокол):
  {"id": "S01", "text": "...", "expected": [{"id": "endometrial_polyp", "quote": "полипа эндометрия"}], "split": "dev"}
  expected = [] означает «норма, находок быть не должно».

Что считаем (на уровне «протокол × тип находки»):
  TP — находка есть в разметке и система её нашла          (правильно)
  FP — системы нашла, а в разметке нет  = ошибка 1-го рода (лишнее срабатывание)
  FN — в разметке есть, система не нашла = ошибка 2-го рода (пропуск — самое опасное)
  Точность (precision) = TP / (TP + FP);  Полнота (recall) = TP / (TP + FN)
Плюс: ложные срабатывания на протоколах-нормах и правильность маршрута.
Результат: таблица в консоли + reports/metrics.csv + reports/errors.csv

scripts/evaluate_ml.py
----------------------

[модуль]
ОЦЕНКА ВТОРОГО КОНТУРА честной кросс-валидацией по протоколам.

Запуск:  python scripts/evaluate_ml.py [data/real/protocols.jsonl] [--repeats 10]

Как считаем (уровень «протокол × тип находки», как в evaluate.py):
  * 5 фолдов, протоколы-дубли/шаблоны в одной группе (поле group), стратификация по типу исследования;
    модель КАЖДЫЙ раз учится без тестовых протоколов. Повторяем с разным разбиением (--repeats).
  * Первый слой (правила) — как есть. Второй контур:
      - детектор пропусков (FN): находки, которых нет у правил (новые + «спасённые» отклонённые);
      - верификатор (FP): помечает принятые правилами находки как «вероятно ложные».
  * Итоговые доли ошибок:
      пропуски (FN-rate)  = FN / (TP + FN)  — доля реальных находок, которые система не показала;
      ложные (FDR)        = FP / (TP + FP)  — доля показанных находок, которых нет в разметке.
Результат: консоль + reports/second_layer_report.md + reports/second_layer_cv.csv
